# ノベルビューア単体テスト拡充スキル

## TDDの進め方

動作を追加・変更するときは、仕様から利用者が観測できる期待結果を決め、最小の失敗テスト（RED）を先に書く。そのテストが期待する振る舞いの違いで失敗することを確認してから、通すための最小実装（GREEN）を行い、成功後に振る舞いを変えずに整理（REFACTOR）する。各段階で対象テストを実行し、失敗原因がテスト準備・環境でないことを切り分ける。

既存実装の未カバー経路へテストを追加し、追加前から成功する場合は、REDを作るためにコードを壊さない。これは既存仕様のカバレッジ拡充として扱い、入力・結果・状態変化・エラーの期待が具体的に検証されることを確認する。テスト名や実装文字列の存在だけを検査せず、内部関数の分割や呼び出し順を不要に固定しない。

## 実行

プロジェクトルートで次を実行する。

```text
node tests/novel_viewer_unit_test.js
```

ブートストラップからテスト単位を指定して実行することもできる。

```text
node tests/run_tests.js unit
node tests/run_tests.js browser
node tests/run_tests.js all
```

PowerShellから各JavaScriptテストを直接呼び出す開発者向けインターフェースも提供する。

```powershell
pwsh -File tests/run_tests.ps1 -Suite unit
pwsh -File tests/run_tests.ps1 -Suite browser
pwsh -File tests/run_tests.ps1 -Suite all
```

`-Suite`を省略すると`all`を実行し、`-Node`でNode.js実行ファイルを指定できる。通常の単体検証では必ず`-Suite unit`を明示する。Firefoxは`firefox`単独スイートで実行し、`all`には含めない。`browser`・`firefox`・`all`はブラウザー操作を含むため、ユーザーの明示指示がある場合だけ実行する。詳細なコマンド・環境条件は[テスト実行ガイド](../../docs/TESTING.md)を参照する。

引数を省略した場合は`all`と同じく全テスト単位を実行する。不明な単位や失敗がある場合は終了コード1以上を返す。

Node.js標準モジュールだけを使用するため、npm installや外部依存は不要である。終了コード0を成功、0以外を失敗とする。

各テスト単位はGoogle Test形式の総括として`[==========]`と`[  PASSED  ]`または`[  FAILED  ]`を表示する。全単位の実行が成功した場合だけブートストラップが`✓ テスト実行成功`を表示する。失敗・例外発生時は終了コード、エラーメッセージ、スタックトレースを記録し、原因を追跡できる形式で報告する。未実施の場合も理由と終了コードを明記する。

テストケースの出力はGoogle Test形式を参考に、`[ RUN ]`、`[ OK ]`、`[ FAILED ]`、`[==========]`、`[ PASSED ]`を使用する。分類はスイート名とケース名で階層化し、総括は実行件数・成功件数・失敗件数を含める。

角括弧付き状態ラベルはGoogle Testに準拠した固定幅で出力し、独自の`ALL`付きラベルは追加しない。

## 文芸的プログラミング

テストコードは文芸的プログラミングの方針で実装する。各スイートは仕様上の章立てに対応させ、テスト名だけで「前提・操作・期待結果」が読める文章にする。複雑な検証は、意図を説明する短いコメント、仕様語を使った補助関数、Given／When／Thenに相当する順序で記述する。

実装詳細の羅列や意味のない短縮名を避け、失敗時のメッセージも利用者が観測する振る舞いを説明する。共通ユーティリティは処理だけを隠蔽し、テスト本体から検証の物語が読める構造を維持する。

仕様語の存在確認だけで単体テストを合格にしてはならない。入力を実際に関数・ユーティリティへ渡し、戻り値、状態変化、例外、境界値を検証する。HTML文字列の確認は実行経路を再現できない場合の補助に限定し、実行可能な処理には必ず動作テストを優先する。

各単体テストは新しい実行コンテキスト、状態、モックを使用し、副作用を後続テストへ伝播させない。HTMLから抽出した関数は呼び出しごとに新しい`vm`コンテキストへ読み込み、共有状態に依存する順序付きテストを作らない。

テスト実行後は成否・例外・中断に関わらず環境を復元する。`finally`でブラウザープロセス、WebSocket、CDP接続、一時プロファイル、ダウンロードディレクトリ、テスト用保存データを削除または閉鎖し、テスト前のユーザーデータを変更しない。

PowerShell実行時の出力エンコーディングは`tests/run_tests.ps1`が一時的にUTF-8へ合わせ、終了時に呼び出し元設定へ復元する。ラッパー外でコードページを変更しない。

Chromium系ブラウザーの操作経路全体を確認する場合は、次を実行する。

```text
node tests/novel_viewer_browser_test.js
```

このブラウザー操作テストはCDPでHTMLを開き、設定、取込、保存、エクスポート、キーボード、狭い画面、オフライン動作などを実際に検証する。ブラウザーがない環境では単体テストのみを実行し、ブラウザー操作テスト未実施であることを結果に明記する。

ブラウザー操作テストとFirefox操作テストは不安定なため、利用者が実行を明示的に指示した場合に限り実施する。テスト変更時も自動実行せず、未実施として報告する。`all`スイートはブラウザー操作テストを含むため、明示指示がない限り使用しない。

ブラウザー操作テストはブラウザーとCDPを自動起動し、既定では動的ポートを`DevToolsActivePort`から取得する。ループバック接続に制限がある場合は`NOVEL_VIEWER_CDP_PIPE=1`で起動パイプを使い、隔離プロファイルを含む全ブラウザーで同じ方式を使う。CDP要求と接続待機に期限を設け、ターゲット取得失敗時にスイート全体を再起動しない。中断シグナルを含む全終了経路で、テストが起動したPIDのプロセスツリー、CDP、一時プロファイル、ダウンロード領域を後始末する。ユーザーが起動したプロセスは終了させない。

状態を待つ検証は固定sleepではなく50ms間隔の条件待ちを使い、遷移・ダウンロード完了時に早く次へ進む。失敗した状態待ち、CDP応答、ブラウザー起動は規定時間内に診断付きで終了する。PowerShellランナーはケースごとの成功を実行中に逐次表示する。

単体テストでは実時間待機を禁止する。処理が時間・タイマーに依存する場合は、その依存を引数で注入し、`tests/test_utils.js`の`createFakeClock()`を使う。`clock.runUntil(waitForCondition(..., { clock }))`で期限・再試行を決定論的に進め、`clock.advanceBy(ms)`で指定時刻までのタイマーを発火させる。実時間の条件ポーリングはブラウザー操作テスト専用とする。新しいタイマー依存機能では、成功・期限切れ・キャンセルなど利用者可視の結果を偽時計で検証する。

ブラウザー操作テストを変更・追加した場合も、実行は利用者の明示指示を待つ。実施した場合は全件成功を確認し、未実施の場合は理由を記録してから完了する。

## テストの分割と実行単位

テストは責務ごとに分割可能な単位で管理する。現在の`tests/novel_viewer_unit_test.js`は依存なしの基準スイートであり、規模が増えた場合は次の群へ分割する。

- `rendering`：Markdown変換、HTMLサニタイズ、リンク、見出し、テーブル
- `persistence`：LocalStorage、IndexedDB、読書位置、タイトル、削除・初期化
- `export`：埋め込みデータ、媒体、ファイル名、復元経路
- `browser`：キーボード、スクロール、テキスト選択、モーダル、Wake Lock
- `ui`：テーマ、アイコン、ラベル、レイアウト、アクセシビリティ

実行する単位は修正の影響範囲で決定する。

1. 単一の純粋処理や局所UIだけの変更は、対応する単体テスト群を実行する。
2. 保存・エクスポート・サニタイズ・共通状態など複数機能へ波及する変更は、関係する単体テスト群を実行する。
3. 仕様書、`AGENTS.md`、共通イベント処理、共通状態、HTML構造を変更した場合は、単体テストを全件実行する。ブラウザー操作テストはユーザーの明示指示がある場合のみ追加実行する。
4. 影響範囲を確定できない場合やテストを分割していない段階では、`node tests/novel_viewer_unit_test.js`で全単体テストを実行する。

部分実行で完了とする場合は、対象単体テスト群と影響範囲を作業結果に記録し、最終的な横断変更では単体テスト全件実行へ切り替える。ブラウザー操作テストは明示依頼時のみ実行する。

## テスト実行資料の更新

テストの追加・削除・分割や実行方法を変更した場合は、[テスト実行ガイド](../../docs/TESTING.md)と[カバレッジマトリクス](../../docs/coverage_matrix.md)を更新する。実行時間は環境差が大きいため、固定値を仕様として扱わない。

## 未検証観点の拡充

単体テストまたはブラウザー操作テストを拡充する場合は、最初に既存テストで検証されていない仕様上の要素を洗い出す。重複検査を増やすのではなく、未検証の不変条件・異常系・境界条件を一つ以上選定する。

検証に共通処理が必要な場合は、`tests/test_utils.js`などの依存なしユーティリティへ集約し、単体テストとブラウザー操作テストの双方から再利用する。HTMLの必須要素・ID一意性、CDPのキー入力と状態確認など、複数テストで使う判定を個別実装しない。

拡充後は、追加したユーティリティ自体の単体テストと影響を受ける単体テストを実行する。ブラウザー操作テストは利用者の明示指示がある場合のみ実行し、それ以外は未実施として結果へ記録する。

拡充の開始時には、仕様書の機能章を行、テストスイートを列とするカバレッジマトリクスを作成する。各交点を「正常系」「異常系」「境界条件」「利用者操作」の観点で確認し、未検証の交点を優先して追加する。実装の文字列を増やすだけの検査は避け、状態変化・安全条件・失敗時の振る舞いを検証する。

作業中に新たな課題が判明した場合は、`AGENTS.md`の課題管理方針に従い、[課題表](../../docs/ISSUES.md)に追加する。解決策が未確定なら候補を記録し、検証結果に応じて確認事実と次の作業を更新する。カバレッジマトリクスには既存テストの対象を記録する。

単体テスト拡充の開始時には、必ず`docs/SPECIFICATION.md`の機能章を一章ずつ読み、仕様上の入力・状態変化・保存結果・エラー処理に対応する単体テストが存在するか確認する。仕様に記載があるのにテストがない観点を不足候補として記録し、実装だけを見てテスト対象を決めない。

マトリクス更新後は、共通ユーティリティで検証可能な不変条件を集約し、単体テストとブラウザー操作テストで同じ前提を再利用する。拡充結果には、追加した観点、対象スイート、未実施の観点と理由を記録する。

## 保守性と開発効率

- 実装中の判定を純粋関数へ分離し、本体と単体テストから同じ関数を使用する。テスト専用に同じロジックを再実装しない。
- テストケースは一つの観測可能な振る舞いだけを検証し、失敗箇所をケース名から特定できる粒度にする。
- 同じ仕様語やソース断片の存在確認を繰り返さない。既存ケースと同じ失敗を検出するテストは統合または削除する。
- 共通の準備・操作・検証は`tests/test_utils.js`へ集約するが、ケース本文から前提・操作・期待結果が読める名前を付ける。
- 変更中は影響する単体テスト群を短く実行し、共通ユーティリティ・仕様書・HTML構造・テスト基盤を変更した場合は最後に単体テスト全件を実行する。ブラウザー操作テストは利用者の明示指示がある場合のみ実行する。
- テスト追加で実装のテスト容易性が低いと判明した場合は、振る舞いを変えずに純粋関数や依存注入境界を追加してから検証する。

## 課題洗い出しから解決までの一連の手順

1. 技術仕様書の機能章、実装、既存テスト、カバレッジマトリクスを突き合わせ、未検証の入力・状態変化・保存結果・エラー処理を課題候補として列挙する。
2. 各候補を利用者影響、データ損失、安全性、再現性で評価し、P0（最優先）・P1（高）・P2（通常）へ分類して優先度順に並べる。以後は先頭の未解決課題を解決対象とする。
3. 課題表に各列の情報を記録し、再現条件と完了条件を明確にする。
4. 解決策を最小単位で実装し、必要なら純粋関数化・共通ユーティリティ化してテスト可能な境界を作る。
5. まず影響範囲の単体テストを実行し、次に必要に応じて単体テスト全件を実行する。ブラウザー操作テストはユーザーの明示指示がある場合だけ実行する。失敗時は課題の状態を検証待ちまたは対応中へ戻し、原因と確認できた証拠を記録する。
6. 検証で完了条件を満たした課題は課題表から削除する。仕様とテストは変更結果に合わせて更新する。
7. 新たな課題が判明した場合は同じ手順の先頭へ戻り、優先度順に課題表を更新する。

## 課題解決の継続条件

- 課題解決を依頼された場合は、少なくとも一つの課題について、実装と検証を完了して「解決済み」とするか、外部依存・再現不能・必要な入力不足などの理由を記録して「解決不可」または「保留」とするまで作業を継続する。
- 解決不可・保留で終了する場合は、試行した手段、確認できた事実、阻害要因、再開に必要な条件を課題表の該当行に記録する。
- 解決済み・解決不可・保留のいずれにも判定できない場合は、課題の切り分け・再現手順・追加ログの収集を続ける。

## 拡充手順

1. 変更対象の実装と仕様書を読み、ユーザーが観測できる不変条件を一つ以上特定する。
2. 既存テストで同じ経路を検証していないことを確認する。重複する文字列検査ではなく、異なる失敗を検出する検査を追加する。
3. 正常系だけでなく、危険な入力・未対応環境・廃止済み経路の再導入を代表する失敗系も追加する。
4. 実装詳細に過度に依存せず、仕様上必要な識別子・属性・安全条件に限定して検査する。
5. `node tests/novel_viewer_unit_test.js`を実行し、全テスト成功と終了コード0を確認する。

### 追加すべき観点

- マークダウン記法：見出し、テーブル、相対リンク、危険なURLスキーム
- HTMLサニタイズ：許可タグ、許可属性、外部リンクの`noopener noreferrer`
- 保存：設定・本文・読書位置・IndexedDBの分離、削除後の復元
- エクスポート：埋め込みメディア、タイトル、外部Blob URLへの依存排除
- UI状態：初期化ボタン、Wake Lock、モーダル表示中の背景操作遮断
- 入力：書字方向別の移動、F1/F11、テキスト選択の維持

ブラウザーDOMを必要とする実動作テストを追加する場合は、外部依存を導入せず、まず対象処理を純粋関数へ分離できないか検討する。DOM依存を静的検査で代替する場合は、検査の限界をコメントまたはテスト名で明示する。

## 検証対象

- 主要ファイルの存在
- マークダウン変換と安全なリンク処理
- LocalStorage・IndexedDBの保存先名称
- F1、F11、S、O、ページ移動ショートカット
- ルビサイズの5%刻み
- Wake Lockステータス表記
- テキスト選択を解除しないクリック処理

機能変更時は実装と仕様を先に更新し、追加した不変条件をこのテストへ反映する。単体テストを拡充した場合は、拡充後のテストを必ず実行し、全件成功を確認する。廃止済みのショートカットや危険なリンク許可を再導入した場合はテスト失敗とする。
