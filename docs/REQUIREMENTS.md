# 宣言的要求

この資料は、ユーザーが望む状態・成果と必須制約を宣言する正本とする。実装手順や作業進捗は記載せず、要求を満たすための計画は[開発計画](./PLANS.md)、個別の未解決作業は[課題表](./ISSUES.md)、利用者から見た確定済みの製品動作は[機能仕様書](./SPECIFICATION.md)で管理する。

## 記載・変更の管理

- ユーザーが要求を直接記載するか、ユーザーが追加・変更を明示的に指示した場合にだけ、この資料の要求を追加・変更する。
- 会話上の個別作業依頼や、実装者が考えた改善案から要求を推定して記載しない。文面の整理を指示された場合も、意図や範囲を変えず、曖昧さが残るときは確認する。
- 要求は望む結果を宣言する。実装方式を指定する必要がある場合は必須制約として明記する。要求IDは[共通採番規則](./IDENTIFIERS.md)に従い、`REQ-001`から順に付け、削除・置換後も再利用しない。
- 要求間、または要求と[開発方針](../AGENTS.md)・[機能仕様書](./SPECIFICATION.md)・他の確定仕様の間に競合があるときは、競合箇所、影響、解消案を示してユーザーに方針を尋ねる。競合する解釈を独断で採用しない。
- 要求は達成後も望ましい状態を表すものとして残す。撤回・置換はユーザーの明示指示で行う。達成状況は開発計画と検証記録で示す。

## 要求一覧

### REQ-001 宣言的要求からの自律開発計画

- **要求**：宣言的要求を満たすため、エージェントが自律して開発計画を立て、計画に沿って開発を進められること。
- **達成条件**：
  - 要求・既存仕様・実装・テスト・関連課題を調べ、要求を観測可能な完了条件へ整理する。
  - 作業の依存関係、優先順、変更対象、検証方法を開発計画に示し、未解決作業は課題表で追跡する。
  - 要求や確定仕様の競合、期待結果が分かれる曖昧さ、必須制約の不足を検出した場合、競合点・影響・解消案を説明してユーザーに方針を尋ねる。競合しない作業は続行する。
  - 方針が確定し、外部への不可逆な操作など別途確認を要する作業がない場合は、通常の実装判断について逐次承認を求めず、実装・必要な文書更新・所定の検証を完了条件まで進める。
  - 完了報告で達成条件ごとの結果と検証状況を示し、未達条件があれば阻害要因・再開条件・次の作業を記録する。
- **制約**：要求の追加・変更はユーザーが直接行うか、ユーザーが明示的に指示する。要求の意味・範囲・優先度・制約をエージェントの判断だけで変更しない。検証方針や安全な実行環境など、[開発方針](../AGENTS.md)の既存ルールを守る。
- **記録元**：ユーザー指示（2026-11-27）。

### REQ-003 依存性注入と単体テスト可能範囲の拡大

- **要求**：依存性の注入を基本とし、単体テストで検証可能な範囲を最大限網羅する。
- **達成条件**：
  - 外部状態、時間、ストレージ、入出力など差し替え可能な依存を注入し、単体テストで実入力に対する観測可能な結果を検証できる構成にする。
  - 変更対象ごとに単体で検証できる動作・境界・エラーを洗い出して検証する。
  - 単体で現実的に再現できないブラウザーAPI・レイアウト・操作は、既存のブラウザー操作テスト方針に従って扱う。
- **制約**：[開発方針](../AGENTS.md)のテスト独立性、TDD、テスト実行条件を守り、内部実装ではなく利用者から観測できる結果を検証する。
- **記録元**：ユーザー指示（2026-11-27）。

### REQ-004 開発ボトルネックの分析と効率化

- **要求**：開発のボトルネックを、時間をはじめとする適用可能な資源面から適宜分析し、効率化する。
- **達成条件**：
  - 作業規模、待ち時間、環境制約、処理量などに応じ、実行時間・CPU・メモリ・I/O・プロセス数・ツール利用など適用可能な指標から制約要因を特定する。
  - 改善前後を同じ条件で比較し、支配的なボトルネックが緩和したか、別の資源へ負荷が移ったかを確認する。
  - 効果が確認できない最適化は採用せず、未解決の制約は課題表または開発知見へ残す。
- **制約**：測定のための作業が本来の作業を不必要に遅らせないよう、分析の深さをボトルネックの影響に応じて選ぶ。ブラウザー操作テストは[開発方針](../AGENTS.md)の明示指示ルールに従う。
- **記録元**：ユーザー指示（2026-11-27）。

### REQ-005 個別の多言語公開HTML

- **要求**：対応言語ごとの公開HTMLを個別に生成し、利用者が選んだファイルの言語で表示すること。
- **達成条件**：
  - 日本語・英語・中国語（簡体・繁体）・スペイン語・フランス語・ドイツ語・ポルトガル語・韓国語・ロシア語・アラビア語・ヒンディー語の個別HTMLを`public/`へ生成する。各公開HTMLには該当言語の辞書だけを含める。
  - ファイル名は`hitohira-jp.html`のように言語接尾辞を付け、READMEの言語別ダウンロードリンクを対応ファイルへ向ける。
  - 各公開HTMLの`lang`・`dir`、フォント名と頭文字アイコン、既定本文を対象言語へ一致させる。アラビア語は右書き方向とする。
  - 日本語と中国語版では縦書き切替を表示する。他の言語版では書字方向操作群と区切り線をDOMから除去し、保存値も横書きに正規化する。
- **記録元**：ユーザー指示（2026-11-27）。

### REQ-006 利用者向け文言・数値書式の多言語品質

- **要求**：対応する12言語すべてで、利用者に見える固定文言を翻訳定義から表示し、翻訳内容と複数形・数値・日付書式の品質を維持すること。
- **達成条件**：
  - 表示文、エラー文、操作名、アクセシビリティ名、タイトル、プレースホルダー、空状態、動的に生成する見出しを含む利用者向け固定文字列は、翻訳辞書のキーを参照する。ソース言語の固定文字列を関数へ直接渡さない。
  - ブラウザーやOSが返す例外文をそのまま利用者へ表示せず、既知の原因は翻訳キーへ対応させ、未知の例外は文脈に応じた翻訳済みフォールバックを表示する。
  - 翻訳キーと置換項目を12言語で揃え、複数形を`Intl.PluralRules`、数値・日付を対象HTMLの表示言語を明示した`Intl`書式で表示する。
  - 用語・文体・プレースホルダーの意味・書字方向を言語別に確認し、静的なキー存在確認に加えて利用者向け出力をテストする。
- **制約**：対応言語と辞書内蔵の公開HTML方式はREQ-005を維持し、本文中の利用者自身の文章は翻訳・変更しない。
- **記録元**：ユーザー指示（2026-11-28）。

### REQ-007 対応言語の用語統一

- **要求**：対応する12言語の用語表を作成し、同じ機能・対象を示すUI表記の揺らぎをなくすこと。
- **達成条件**：
  - 設定、検索、本文、目次、しおり、書体、書字方向、インポート、エクスポート、ファイル種別など主要な反復用語を12言語で記録する。
  - 中国語簡体字・繁体字を分け、用語族の文法的な活用と許容される文脈差を定める。
  - 対応辞書キーの代表訳と用語表を単体テストで照合し、同義キー・用語族の表記揺らぎを回帰検出する。
- **制約**：文法上必要な格・数・語順の変化は許容し、同義語への任意な置換を避ける。既存の利用者向け用語・表示言語仕様を維持する。
- **記録元**：ユーザー指示（2026-11-28）。
